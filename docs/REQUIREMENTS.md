# 요구사항

## 문제 정의

- 클라이언트는 증권 주문 요청을 우리 서버로 보낸다.
- 서버는 실제 주문 제출과 체결 상태 확인을 외부 증권사 API에 위임한다.
- 외부 증권사 API는 응답 지연, 인증 만료, 일시 장애가 있을 수 있다고 가정한다.
- 클라이언트는 주문 작업의 진행 상태, 최종 결과, 작업 목록을 조회할 수 있어야 한다.

## 범위

- 포함:
  - Java 17 + Spring Boot 기반 백엔드 서버 구현
  - 주문 작업 접수 API
  - 작업 식별자 발급 및 추적 가능한 조회 API
  - 작업 상태 조회, 결과 조회, 목록 조회
  - 외부 증권사 API 토큰 발급, 주문 제출, 상태 조회 연동 구조
  - 실패 표현, 중복 요청 처리, 상태 전이, 처리 보장, 재시작 동작 정의
  - 테스트 코드, 컨테이너 실행 환경, README/ADR/런북 작성
- 제외:
  - 프론트엔드 구현
  - 실제 증권사 내부 로직 수정
  - 계좌 인증, 사용자 인증/인가, 출금/정산 도메인
  - 상용 실계좌 자격 증명을 강제하는 구성
  - 실시간 WebSocket 체결 푸시

## 기능 요구사항

- 작업 접수:
  - 주문 요청을 받는 API를 제공해야 한다.
  - 클라이언트가 이후 조회에 사용할 작업 식별자를 반환해야 한다.
  - 주문 요청에는 증권사 코드, 계좌번호, 종목코드, 매수/매도, 주문유형, 수량, 가격이 포함되어야 한다.
- 작업 상태 조회:
  - 클라이언트가 작업 진행 상황을 확인할 수 있어야 한다.
  - 상태 모델은 직접 정의해야 하며 각 상태의 의미가 문서화되어야 한다.
- 작업 결과 조회:
  - 완료된 작업의 결과를 조회할 수 있어야 한다.
  - 성공 시 증권사 주문 ID, 체결 수량, 평균 체결 가격을 확인할 수 있어야 한다.
  - 실패한 작업은 실패 사실과 원인을 식별 가능하게 표현해야 한다.
  - 결과 보존 기간이 지난 terminal job은 cleanup 이전이라도 조회 시 `404 Not Found`로 취급되어야 한다.
- 작업 목록 조회:
  - 클라이언트가 작업 목록을 조회할 수 있어야 한다.
  - 정렬, 페이징, 필터링 정책은 설계자가 정하되 README에 명시해야 한다.
  - 보존 기간이 지난 terminal job은 cleanup 이전이라도 목록에서 제외되어야 한다.
- 외부 연동:
  - 토큰 발급, 주문 제출, 주문 상태 조회를 별도 증권사 API 클라이언트 계층으로 분리해야 한다.
  - 증권사 API의 인증 실패, timeout, `4xx/5xx`, 일시 장애를 운영 조건으로 다뤄야 한다.
  - 기본 연동 path는 환경 변수로 변경 가능해야 한다.
- 문서화:
  - README에 설계 의도와 주요 판단 근거를 포함해야 한다.
  - 실행 방법, 포트, 필요한 환경 변수와 컨테이너 구성을 명확히 적어야 한다.

## 상태 모델 요구사항

- 전체 상태 집합을 정의해야 한다.
- 허용되는 상태 전이와 허용되지 않는 상태 전이를 명시해야 한다.
- 성공과 실패를 포함한 종료 상태를 구분해야 한다.
- 외부 증권사 주문 상태(`PENDING`, `PARTIALLY_FILLED`, `FILLED`, `REJECTED`, `CANCELLED`)를 내부 작업 상태와 어떻게 연결하는지 설명해야 한다.
- 재시도나 복구가 있다면 상태 전이에 어떻게 반영되는지 설명해야 한다.

## 중복 요청 처리 요구사항

- 동일 주문 요청이 여러 번 들어올 수 있음을 전제로 해야 한다.
- 어떤 기준으로 동일 요청을 판단할지 정의해야 한다.
- `Idempotency-Key` 누락, 형식 오류, 재사용 충돌을 어떻게 구분해 표현할지 정의해야 한다.
- 유효한 새 요청은 `QUEUED`를 반환하고 이후 비동기 처리로 넘어간다는 점을 설명해야 한다.
- 같은 `Idempotency-Key` replay는 기존 job의 현재 상태를 그대로 반환해야 한다.
- 주문 작업 조회 응답에서는 계좌번호를 마스킹해야 한다.

## 처리 보장 및 장애 복구 요구사항

- 시스템의 처리 보장 모델을 명시해야 한다.
- 그렇게 판단한 근거를 설명해야 한다.
- 서버 재시작 시 진행 중 작업이 어떻게 되는지 설명해야 한다.
- `PROCESSING` 상태가 무기한 지속되지 않도록 attempt 단위 종료 또는 재시도 기준을 정의해야 한다.
- 데이터 정합성이 깨질 수 있는 시점과 완화 전략을 기술해야 한다.

## 가정

- 명시된 가정:
  - 외부 증권사 API의 엔드포인트와 토큰/주문/상태조회 스펙은 계약 기간 동안 고정돼 있다고 가정한다.
  - 증권사 API는 sandbox 또는 사내 mock/stub로 대체 가능해야 한다.
  - 주문 체결 여부는 즉시 확정되지 않을 수 있다.
- 도출된 가정:
  - 주문 접수 API는 외부 체결 완료까지 동기적으로 블로킹하지 않는 방향이 적합하다.
  - 주문 메타데이터는 제출 후 조회 가능해야 하므로 서버는 작업 이력을 보존해야 한다.
  - 외부 API 인증 토큰은 만료될 수 있으므로 캐시와 재발급 전략이 필요하다.
  - 계좌번호는 저장되더라도 read API에서는 마스킹해 노출하는 편이 안전하다.

## 비기능 요구사항

- 신뢰성:
  - 순간 트래픽 증가나 증권사 API 지연이 있어도 작업 상태가 유실되지 않도록 설계해야 한다.
  - 외부 호출 실패, timeout, 중복 요청, 서버 재시작 시에도 상태 일관성을 유지해야 한다.
- 보안:
  - 증권사 API key/secret과 access token을 코드에 하드코딩하지 않고 설정값과 런타임 메모리 캐시로만 관리해야 한다.
  - 계좌번호는 목록/상태/결과 조회 응답에서 마스킹해야 한다.
- 성능:
  - 주문 접수 및 조회 API는 장시간 외부 처리에 직접 묶이지 않아야 한다.
  - 트래픽 증가 시 병목 지점과 보호 전략(예: batch size, executor queue, retry backoff)을 설명해야 한다.
- 운영성:
  - 테스트 코드로 핵심 동작을 검증해야 한다.
  - `./gradlew test jacocoTestReport`로 재현 가능한 coverage report를 생성할 수 있어야 한다.
  - 컨테이너 환경에서 재현 가능하게 실행되어야 한다.
  - 디버깅 절차와 실행 방법이 문서화되어야 한다.

## Java 코드베이스 가드레일

- main source 와 test source 는 Java 17 기준으로 유지한다.
- 공개 API contract, status 이름, error code, pagination/filter semantics 는 브레이킹 체인지 없이 유지한다.
- read API 의 account number masking 은 클라이언트 계약의 일부로 본다.
- 토큰 lazy issuance, `401` refresh retry, timeout/backoff, single-step `PROCESSING` continuation, stale recovery semantics 는 유지한다.
- 증권사 API path 또는 인증 헤더가 바뀌면 README, ADR, API 문서, 런북, `.env.example`, `docker/compose.yaml`를 함께 갱신한다.
